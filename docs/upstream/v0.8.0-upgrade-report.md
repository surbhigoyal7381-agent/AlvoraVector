# Upgrade report: Fleetbase v0.7.75 to v0.8.0

Prepared 18 Nov 2026 by vector-upstream-sync. Advice only; Surbhi decides.
Compared: `origin/dev` (67b2db6, v0.7.75) against `upgrade/fleetbase-v0.8.0` (23d9e2e1 = upstream tag `v0.8.0`; 9 upstream commits, fast-forward). Read with `git show`/`git diff` against refs.

## 1. What this means for us (read this first)

**Recommendation: merge v0.8.0 to `dev` now.** It is a clean fast-forward, we carry no code on top of it, and the local stack already runs it. Nothing runs automatically on a push to `dev` (verified: the two changed workflows add test steps but no new triggers). A later `dev` to `main` pull request does not release or publish, because `release.yml` tags only when the merged branch is `release/v*` or `dev-v*`.

- It is a big jump underneath (Laravel 10 to 12, PHP 8.2+), but for a stack with no data to protect and no extensions of ours, the cost is low. The real cost lands on whoever writes extensions or the ERPNext connector later: they build against the new version from day one.
- **Next step: v0.8.1 is already out** (tag `v0.8.1`, 022238c5, plus 90d9d6b4 "retry the PHP extension install when PECL or apt fails"). It is a small dependency release (core-api 2.0.2, Fleet-Ops 0.7.1, ember-core 0.3.27, ember-ui 0.4.7). Its main fix is that migrations fail on MySQL 8.4; our Compose uses MySQL 8.0, which was never affected. Not prepared here; assess it as the next slice.
- **Trap to fix: image drift.** The API runs from the `fleetbase/fleetbase-api:latest` image, while the console builds from our checkout. On 18 Nov they drifted (v0.8.0 API with a v0.7.75 console until the console was rebuilt). Recommend pinning the image tag to the release we merged.
- **Upstream installer bug, still present in v0.8.1** (candidate upstream PR, see section 6).
- No security defaults changed that I could find (socket auth, throttles, key handling): none appear in `RELEASE.md` or in the changed files. See "Not checked".

## 3. What changed, per component

Source: `RELEASE.md` at the tag, which I read. I did not read each module's own changelog or code (modules are not in this checkout).

- **core-api 2.0.0:** Laravel 12, Sanctum 4, Carbon 3; `Request::array()` renamed `inputArray()`; Doctrine DBAL removed; FCM push on kreait/laravel-firebase 6; new majors of Fleetbase's forks (mysql-spatial 2.0, countries 0.9, twilio 6.0).
- **fleetops 0.7.0:** order config policies (how adhoc orders are offered, driver matching by vehicle type, what customers may do, re-pricing from actual distance and time); triggers (actions when an order reaches an activity, is created, completed, cancelled, no driver accepts, driver nears pickup or drop-off); templates (`transport`, `passenger`; `php artisan fleetops:create-order-config {template} --company=`); new Customer API (places, sign-in codes, an order's dispatch, cancel, driver, tracker, ETA, chat with driver, ratings, tracking links, account deletion).
- **ledger 0.1.0:** a Fleet-Ops order's customer can fetch and pay its invoice; a paid invoice settles the order's transaction; new `send_invoice` trigger action; cash gateway can be staff-confirm only.
- **storefront 0.5.0, customer-portal 0.1.0, registry-bridge 0.2.0, ai/valhalla/vroom 0.1.0:** released for Laravel 12 and core-api 2.0 (that is all the notes say).
- **ember-ui, ember-core, dev-engine, iam-engine:** unchanged in `RELEASE.md` (same versions as before). fleetops-data 0.2.3 to 0.2.4.
- **socket:** no change in the diff (nothing under `socket/`).
- **Shell files changed (verified in the diff):** `api/bootstrap/app.php` (adds `$app->dontMergeFrameworkConfiguration()`), `api/config/cache.php` (default cache prefix now ends in `:`), `api/composer.json` and `.lock`, `console/package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml` (version pins and the new `ai-engine@0.1.0` release-age exclusion), `docker/Dockerfile` (`FLEETBASE_VERSION=0.8.0`), `.github/workflows/api.yml` and `api-contract.yml`, `.github/contract-stacks/l12.json`, `scripts/ci/assert-migrated.sh`, `scripts/ci/resolve-contract-stack.py`, ERD files (`database.mmd`, `erd.svg`, `erd-dark.svg`), `RELEASE.md`, and 9 submodule pointers (ai, core-api, customer-portal, fleetops, fleetops-data, ledger, pallet, registry-bridge, storefront). The submodules are not initialised here and the build installs from Composer and npm, so the pointers do not affect the build.

## 4. Breaking changes (from `RELEASE.md`)

- Extensions built for core-api 1.6.x will not install. All bundled ones are updated; any extension from the registry must be updated.
- `Request::array()` is now `inputArray()` (custom code).
- Carbon `diffIn*` now returns signed floats (custom code).
- Laravel 12 merges its own default config unless the app opts out: keep `$app->dontMergeFrameworkConfiguration()` in `api/bootstrap/app.php` (already there in v0.8.0). Without it the API connects to 127.0.0.1 instead of `DATABASE_URL`.
- PHP 8.0 and 8.1 are no longer supported.
- Laravel 10 installs can stay on v0.7.75.

## 5. Migrations

- `RELEASE.md`: migrations run on deploy; core-api adds a guarded `personal_access_tokens` migration that does nothing when the table exists, so existing API tokens keep working.
- Fleet-Ops 0.7.0 adds adhoc-dispatch / order-config tables and columns (the ERD files changed). **Not checked:** the migration files themselves, their locking behaviour, and time on a copy of data (modules not in this checkout).
- Known upstream defect, fixed in v0.8.1 (read in its `RELEASE.md`): the Fleet-Ops adhoc dispatch migration fails on **MySQL 8.4** (`1553 Cannot drop index`), leaving it half applied. Our Compose uses MySQL 8.0, which upstream says is not affected. If anyone runs 8.4 anywhere, go straight to v0.8.1.
- The local stack migrated from v0.7.75 data and runs; the main session's test results below say how clean it was.
- Reversibility: no rollback tool was read. Back up the database before any shared environment upgrade (`RELEASE.md` says so); a downgrade is a restore.

## 6. Config and env changes

- `CACHE_PREFIX`: default now ends in `:`. If anyone sets `CACHE_PREFIX` without a trailing `:`, flush the cache. **Checked 18 Nov 2026: all three values in `docker-compose.yml` end in `:` (`laravel_cache:` for queue/scheduler, `fleetbase_cache:` for application, confirmed at runtime), so no flush is needed.**
- Octane workers must restart to load the new framework (restart API, queue, scheduler, events containers).
- `docker/Dockerfile`: only the version string changed in v0.8.0. (v0.8.1 reworks the extension install with retries.)
- CI: `api.yml` gains a "Fresh MySQL Migrate" job (MySQL 8.0 and Redis services); `api-contract.yml` and `l12.json` add a contract stack that links the modules from their tags. No new triggers.
- **Upstream installer bug (verified present at v0.8.0 and unchanged in v0.8.1; `git diff v0.8.0 v0.8.1 -- scripts/docker-install.sh` is empty):** `scripts/docker-install.sh` writes `DATABASE_URL`/`APP_KEY` into `docker-compose.override.yml` for `application` only. `queue` and `scheduler` keep `mysql://root@database/fleetbase` with no password, so the queue worker crash-loops ("Allowed memory size exhausted" at Connector.php) and every background job fails. Fixed locally by copying the env block to both. Candidate upstream PR (general, small). Same family as the `APP_NAME` gap already in the ledger.
- Cosmetic: the scheduler container shows "unhealthy" because its healthcheck curls Caddy on :2019, which it does not run.
- Push notifications (FCM) fail locally: no Firebase configured. Expected.

## 7. Effect on our extensions and the ERPNext connector

- **Our extensions:** none exist, so nothing breaks. Any future one must target core-api 2.0 (Laravel 12, `inputArray()`, signed Carbon diffs).
- **Connector (outside Fleetbase, REST and webhooks; not built yet).** What v0.8.0 changes that it could touch, from `RELEASE.md` only:
  - Order config triggers and the new Customer API are new surface; the Customer API is for customer-facing apps, not obviously for a connector.
  - Ledger invoice and payment changes (customer can pay, paid invoice settles the order's transaction, `send_invoice` trigger) overlap with what ERPNext invoicing would do. Decide early who owns invoices.
  - **Webhook payload shape, REST payloads and auth: the notes do not mention any change. I could not confirm that none changed** (needs the core-api and fleetops code or API reference at v0.8.0). Build the connector's contract tests against the running v0.8.0 stack, not from memory.
  - Sanctum 4: existing API tokens keep working (guarded migration), per the notes.
