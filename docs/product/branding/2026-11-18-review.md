# Review: rename to "Alvora Vector" (option B)

Date: 18 Nov 2026 · Reviewer: vector-technofunctional-reviewer · Risk tier 2 · Branch `feature/alvora-vector-brand`, `main..HEAD` = 1721e228, 138e82f7, e1f5b414, 9a5e1f1d (55 files, +1126/-211). Base `main` = 23d9e2e1 (v0.8.0).

## 1 · Verdict

**BLOCK, because of one config line set, not the console work.** The `APP_NAME` change in `docker-compose.yml` moves the API's Redis key prefix but not the queue worker's. Queued emails and notifications then never get sent. The fix is about six lines in `docker-compose.yml`. The console rebrand itself (translations, overrides, brand check, hard-coded text) is ship quality once the P2 below is decided.

Process note: there is no impact analysis (`00-impact-analysis.md`) for this change. The PM recommendation and the implementation notes stand in for it, and neither looks at what `APP_NAME` drives inside the API. That missing step is what let B1 through.

## 2 · Blockers

### B1 (P1) · `docker-compose.yml:132-133`: the app and the queue worker now read different Redis queues

**Proven** by booting the API image's config with and without the variable (`docker run ... fleetbase/fleetbase-api:latest`, Laravel bootstrapped, `config()` printed):

```
APP_NAME=Alvora Vector  redis.prefix=alvora_vector_database_  cache.prefix=alvora_vector_cache:  session.cookie=alvora_vector_session
APP_NAME=<unset>        redis.prefix=fleetbase_database_      cache.prefix=laravel_cache:        session.cookie=laravel_session
```

- The prefix comes from `api/config/database.php:82` (and `core-api/config/database.redis.php:32`): `env('REDIS_PREFIX', Str::slug(env('APP_NAME','fleetbase'),'_').'_database_')`. The queue uses that connection (`config/queue.php` `redis.connection = default`).
- In the tracked `docker-compose.yml`, only `application` sets `APP_NAME`. `queue` (lines 79-100) and `scheduler` (57-77) do not. The image bakes in no `.env` and no `APP_NAME` (checked: only `.env.example` exists).
- **On `main`** the app had `APP_NAME: Fleetbase`, which gives `fleetbase_database_`. The worker's default is also `fleetbase_database_`, so the two matched (by luck).
- **On this branch** the app pushes to `alvora_vector_database_queues:default` and the worker pops from `fleetbase_database_queues:default`.
- Failure scenario: someone runs `docker compose up` from the tracked file with no override that sets `APP_NAME`. A user clicks "Forgot password" or an order is assigned. `UserForgotPassword`, `UserInvited`, `PasswordReset`, `OrderAssigned`, `OrderDispatched` and others all implement `ShouldQueue` (grep in `api/vendor/fleetbase`). The job lands in a queue nobody reads. No error appears anywhere, and riders and customers simply get nothing.
- Second effect, even with the prefixes aligned: queued mail is rendered **in the worker**, where `config('app.name')` falls back to `'Fleetbase'` (`config/app.php:16`). So most emails and SMS (`VerificationMail`, `TwoFactorAuth.php:362`, the `mail.blade.php` footer "© {year} {app.name}", the fleetops driver/customer codes) would still say Fleetbase. The change does not achieve what the ledger row claims ("emails and 2FA label read Alvora Vector").
- Why it was not seen: Surbhi's git-ignored `docker-compose.override.yml` sets `APP_NAME: "Fleetbase"` on all three services. On her stack this compose change therefore has **no effect at all**, neither the bug nor the rename. The API tests (44 pass) never start a worker. This is lesson 2: the evidence could never show the behaviour.
- The same split hits the real deployment later. The current `scripts/docker-install.sh` writes `APP_NAME` into the override for `application` only (line 461). Once Surbhi enters "Alvora Vector" at its prompt (lines 108, 124, default still "Fleetbase"), the queue splits the same way. That installer gap is upstream's, but this rebrand is what makes a non-"Fleetbase" name normal.

**Smallest fix (in `docker-compose.yml` only):** set `APP_NAME: Alvora Vector`, `MAIL_FROM_NAME: Alvora Vector` **and** `REDIS_PREFIX: fleetbase_database_` on `application`, `queue` and `scheduler`.
- Pinning `REDIS_PREFIX` keeps the queue and any existing Redis data on the old keys, so no orphaned jobs and no cold cache on a future switch.
- Optionally pin `CACHE_PREFIX: fleetbase_cache:` and `SESSION_COOKIE: fleetbase_session` on `application`. That keeps the change strictly "name only" and avoids a one-time logout of cookie sessions (Inferred: the console mostly uses bearer tokens, so the logout is a small effect).
- Add a line to the ledger row explaining why the prefix is pinned.
- **Question for Surbhi (should know):** should the installer's default name become "Alvora Vector"? That means editing `scripts/docker-install.sh`, an upstream file (rung 4, one more divergence row). If not, write in the notes that the name for a real install is set in the override, on all three services.

## 3 · Majors

### M1 (P2) · The tracking-page toggle now promises "Powered by Alvora Vector", but customers see "Powered by Fleetbase"

**Proven.**
- `console/translations/brand-overrides/en-us.yaml:57-60` (and the same keys in es-pa, mn-mn, pt-br, vi-vn and the other override files) rename `tracking-page.settings.powered-by` ("Show "Powered by Alvora Vector"") and `preview-powered-by`.
- The public tracking page does not use a translation for this. `fleetops-engine/addon/components/tracking-page.hbs:125-127` renders `<FleetbaseAttribution @showPoweredBy={{true}} />`. In `ember-ui/addon/components/fleetbase-attribution.hbs:3-4` that shows the hard-coded "Powered by Fleetbase v0.8.0 · Legal", linking to `https://www.fleetbase.io`.
- `tracking-page.page.powered-by` is not referenced anywhere in the fleetops addon (grep), so renaming it changes nothing.
- Failure scenario: an operator admin opens Settings > Tracking page. The toggle and preview read "Powered by Alvora Vector", and it is on by default (`tracking-page-settings.js:36`, `?? true`). Their end customers see "Powered by Fleetbase · Legal" on every tracking link. The operator was told something false about a customer-facing surface.
- It also hides the fact that this toggle is what shows or hides the Fleetbase legal attribution on the public page. That matters for the counsel question about the legal notice (AGPL §5(d)).

**Fix:** keep those two settings strings naming Fleetbase. Add them to the keep-list in `brand-rules.mjs` by full key (`ALLOW_LEAF_KEYS` is leaf-name based, and `powered-by` as a leaf would also cover the unused `page.powered-by`, which is acceptable). Then regenerate. **Decision for Surbhi:** confirm the toggle should read "Show "Powered by Fleetbase"". Ranked P2 meanwhile.

## 4 · Minors

**m1 (P3) · Two locales renamed "Fleetbase CLI", which the decision keeps.** `console/translations/it-it.yaml:874` ("dalla CLI di Alvora Vector") and `uk-ua.yaml:878` ("через CLI Alvora Vector"). The keep-phrase `/Fleetbase CLI/` only matches the English word order. Failure scenario: an Italian or Ukrainian admin on the not-installed page is sent to a tool that does not exist. The brand check cannot see this kind of error: it looks for leftover names, not for names replaced where they should have stayed. Fix: restore the two lines.

**m2 (P3) · Overrides freeze upstream wording without anyone noticing.**
- `brand-overrides.mjs:9` says "`pnpm lint:brand` fails when they are stale". That is only true for *new* Fleetbase strings.
- Failure scenario: upstream edits an engine string that still names Fleetbase, for example fixing a wrong instruction or adding a `{placeholder}`. The committed override still has the old text and no "Fleetbase", so `brand-check.mjs` (lines 33-45) passes. Users keep the old, possibly wrong, text after every upgrade.
- The same happens when upstream removes "Fleetbase" from a string: our old copy still wins.
- Fix: in `brand-check.mjs`, regenerate the overrides in memory and fail if they differ from the committed files. That is about 10 lines; I ran exactly this comparison for this review (see §6) and it is cheap.
- The ledger row ("an engine adds or renames a string: lint fails") should say the same.

**m3 (P3) · Grammar from mechanical replacement.**
- English: `brand-overrides/en-us.yaml:16-17` "a Alvora Vector account" in the IAM invite modal, which admins read on first use.
- French: `fr-fr.yaml:794` "auprès de Alvora Vector" should be "d'Alvora Vector"; `brand-overrides/fr-fr.yaml:17,28` "que Alvora" should be "qu'Alvora".
- Bulgarian: "във Alvora Vector" should be "в Alvora Vector" in `bg-bg.yaml:583,770,788,795` and `brand-overrides/bg-bg.yaml:26`.
- pt-br mixes "o Alvora Vector" and "a Alvora Vector" (inherited from upstream's own mix).
- Placeholders, plurals and YAML are intact (see §6). Fix: put the English article fix (and French, if wanted) into `rebrand()` as locale-aware post-replacements, or hand-write those keys in the host file, which the generator then skips.

**m4 (P3) · SMS sender example breaks its own rule.** `console/app/templates/console/settings/notifications.hbs:36` gives "Alvora Vector" as an example sender ID. Lines 33 and 37 say "up to 11 letters or numbers"; "Alvora Vector" is 13 characters with a space. An operator who copies the example gets a sender ID carriers reject. Fix: use "AlvoraVec", or drop our name from the example.

**m5 (P3) · The divergence ledger is partly stale.** `docs/upstream/divergence.md`:

**m6 (P4) · Some registry text is now untrue.** In the `registry-bridge` overrides ("self-managed-help-text", en-us and other locales), "the cloud/SaaS version of Alvora Vector" describes Fleetbase's cloud and registry, and Alvora Vector has no cloud/SaaS version. None hides a current leftover: my independent scan found nothing.

## 7 · What to delete

Nothing structural. Three small scripts and one generated folder is the right size for keeping 228 engine strings in sync. One cut: the `--dist` mode of `brand-check.mjs` (lines 70-87). It parses `vendor.js` with a regex, is not wired to CI, and duplicates the merged-source check. It is useful as a one-off proof, but optional to keep.

## 8 · What was done well

- Generating overrides from the installed packages instead of hand-copying 228 keys, with host text always winning.
- The check merges in ember-intl's own order, including the en-us fallback and an engine-only locale (es-pa). That is how the es-pa gap was found.
- Keeping hosted-routing text truthful for privacy reasons, and leaving the legal notice untouched.
- The negative proof: the check was shown to fail when the name was put back.
