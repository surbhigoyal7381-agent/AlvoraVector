## How the engine overrides work

ember-intl merges engine translations first and the host app last, so a key in the host wins. Files in `console/translations/brand-overrides/` are discovered like any other host file: ember-intl takes the locale from the file name and merges all files of the same locale (verified by a build: the keys appear in the built bundle). They are separate from the hand-written host strings, and a key the host already defines is skipped, so hand-written text always wins.

Script usage (Node 22, from `console/`):

- `pnpm brand:overrides` regenerates every override file from the installed `@fleetbase/*` packages. Run it after every upstream upgrade (after `pnpm install`) and commit the result.
- `pnpm lint:brand` is the check. It merges engines + overrides + host the way ember-intl does and fails if any value in any locale still names Fleetbase. It also scans the console's own templates and scripts, `index.html`, the manifest and `docker-compose.yml`. `pnpm lint` runs it, so CI (`console.yml`) calls it. `node scripts/brand-check.mjs --dist` additionally scans a built `dist/`.
- Allowed on purpose (`brand-rules.mjs`): the hosted-routing label and help text (they describe data sent to Fleetbase Cloud; changing them would make a privacy statement false), the phrase "Fleetbase CLI", and four console files that show Fleetbase's own content (the Fleetbase Blog and GitHub widgets, a debug log prefix, PHP class names in a comment). The legal notice and attribution live inside `@fleetbase/ember-ui` and are untouched (`DISABLE_FLEETBASE_ATTRIBUTION` is not set).
